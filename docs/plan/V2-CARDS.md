## Recommendations to honour (Nitin, 9 Oct; from the data-model review) — reviewers check every card against these

1. **Cut-off discipline.** A calculation run with `knowledge_cutoff_at` = 6 Oct may use only rows recorded by then (VAL-1). A run after the revision may consider VAL-2 **subject to validation**: an unverified value never enters a certified metric; it appears only as draft or indicative with its status.
2. **Before verification, people are told.** When the amended statement is read and its value is still pending review: an exception "Investigate the 180,000 USD manager-reported valuation difference" opens; Operations gets a verification task in Pulse; the CIO sees an indicative change clearly labelled **unverified**. Confirmation by Operations then records the valuation and moves the case on. (Today E2b records the valuation only on confirm, so the exception and Pulse must also be raised at extraction time.)
3. **Wording.** 10.18m minus 10.00m is a change in the **manager-reported valuation**, never "P&L rose by 180,000" and never a change to official NAV. Every screen, Pulse card, case title, explanation and brief must say it that way.
4. **Official NAV is untouched.** `nav_snapshots` changes only when a separate approved NAV or restatement arrives from the administrator. No agent and no rule writes it.
5. **Never update history.** No UPDATE to a source record, an observation, a calculation run, a metric value or an issued report's lines. Append a new version and keep the old one. Only workflow state columns move, each with an event row.
6. **Tenant consistency.** Every referenced row belongs to the same organization. Each company has its own warehouse file, and `e1_write` must also check that any id a row references exists in that warehouse (and, at the client on PostgreSQL, composite tenant keys plus row-level security).
7. **Exactly one evidence pointer.** Each `metric_evidence` row references exactly one of source record, document passage or extracted field (E1c currently stores some as a note; fix to a real pointer or a documented single pointer rule enforced in code and tested).
8. **Exactly one approval target.** Each `approvals` row references exactly one target (intent, calculation run, exception, report version, rule version or sheet mapping), enforced in code and tested.
9. **Build order of tables.** Organizations and users, portfolios and instruments, sources and batches and records, documents and passages, valuations and NAV and positions, intents and runs and metrics and evidence, exceptions and events and approvals and Pulse and agent runs come first; transactions, cash movements, market observations and benchmark composition are used only where phase 1 needs them (FX for USD/SGD, the cash recon) and are otherwise left for after the first end-to-end revision flow works.
