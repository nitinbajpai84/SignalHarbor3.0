# Signal Harbor · four centres, three agents (build cards, 9 Oct 2026)

Decided by Nitin (9 Oct): keep the centres, make them clean, and cut the agents to three.

| Centre | What a person does there | Agent |
|---|---|---|
| **Intent** | Says what they need in a conversation; North drafts the intent of work, the swim-lane process map and the definitions, and records which sources and files (structured and unstructured) the work needs. Creates the project id. | **North** (intent agent) |
| **Action** | Today's cards, cases with evidence, reconciliations, approvals. What changed, who owns it, what to do next. | none of its own; reads what the other two produce |
| **Build** | Picks a project. Span (the build agent: architect, data modeller and data engineer in one) reads the intent and the current data model and proposes model changes, bronze/silver/gold tables, SQL, a high-level diagram; the head of data approves; Span builds and runs the pipeline; a schedule says how often. Ingesting new structured or unstructured files happens here. | **Span** (build agent) |
| **Consume** | Picks a project. Sees the gold tables it produced. Tells Lumen the KPIs and how they should look (words, or a picture of the visual they want). Lumen proposes tiles; the person accepts; the dashboard is shared with named people. | **Lumen** (consume agent) |

Flow, Jev (as a persona), the investigation and briefing agents are retired as names. Their code stays: document reading and extraction become Span's tools; explanations and briefs become Lumen's tools; Jev stays an internal classifier with no face.

## Facts settled (every builder follows these)

1. Repo `<repo>`, not git, no worktrees. Read `CLAUDE.md`, `.claude/rules/house-style.md`, `data-locality.md`, `egress.md`. Use graft. Card pattern as in `docs/plan/V2-CARDS.md` (backend `sh_platform/v1/<id>_*.py` + `<id>_routes.py` + `<id>.permissions.yaml`; UI `ui/src/v1/<id>/routes.tsx`; tests `tests/v1/test_<id>.py`; landing `docs/plan/v3-landings/<ID>.md`). All facts settled in `docs/plan/V2-CARDS.md` still hold (warehouse only via `wh.py`, `e1_write.org_id`, append-only, egress, no model arithmetic, maker and checker different people).
2. **Routes of the four centres** (exact): `/centre/intent`, `/centre/action`, `/centre/build`, `/centre/consume`, plus `/centre/settings`. Project pages: `/centre/build/p/:projectId`, `/centre/consume/p/:projectId`. Old entry paths redirect (card S1 owns redirects).
3. **Projects** are the existing P1 projects (`sh_platform/v1/p1_project.py`: `create_project`, `for_intent`, `project_of`). A project id is the thread through all four centres. Build and Consume always start with a project picker (shared component `ui/src/v1/s1/ProjectPicker.tsx`, card S1).
4. **Layers** (card D1 owns the definition): **bronze** = raw rows as landed, one table per source layout, named `bronze_<source_code>_<layout>`; **silver** = the canonical model in `docs/v2/evidence-to-action-mvp.dbml` (the current 41 tables, unchanged names); **gold** = per-project marts named `gold_<project_slug>_<name>`. The catalogue (`e0a_catalogue`) records each table's layer, owner project (gold) and source (bronze). Helpers: `e0a_catalogue.layer_of(plane, table)`, `tables_for_project(plane, project_id) -> {bronze:[], silver:[], gold:[]}`.
5. **Build plan** (card B2 owns): one JSON record per project version at `data/<company>/build/<project_id>/plan-v<n>.json`: `{project_id, version, sources:[{code, kind: structured|unstructured, files, owner}], model_changes: <E0a proposal id or null>, tables:[{name, layer, purpose, columns:[{name,type,from}], sql, depends_on:[table]}], lineage:[{from, to}], schedule:{freq: daily|weekly|monthly|on_arrival, at:"06:00", day:null}, state: draft|proposed|approved|rejected|built|live, proposed_by, approved_by, approved_at, reason}`. SQL is DuckDB, SELECT-based CREATE TABLE AS / INSERT, reads only bronze/silver/gold tables named in `depends_on`; the program validates every referenced table and column against the catalogue before saving.
6. **Approval**: a build plan and any model change are approved by the **head of data** (architect seat) who is never the proposer; one approval covers the plan and its linked E0a model change (approving the plan approves the model change through `e0a` in the same step). Every approval is logged.
7. **Pipeline runs** (card B4 owns): run a plan's tables in dependency order on the company warehouse; first in a sandbox copy (`warehouse/sandbox.duckdb`), live only when the plan is approved. Run log at `data/<company>/build/<project_id>/runs.jsonl` (`{run_id, plan_version, started, finished, status, steps:[{table, rows, ms, status, error}]}`). Scheduler: stdlib thread in the server, checks every minute, runs plans whose schedule is due; `on_arrival` runs after a load of a file whose source the plan uses. Every plan also exports an Airflow DAG file `airflow/<project_slug>.py` for the client deployment (one task per table, same dependencies, same schedule) — generated text, not executed locally.
8. **Dashboards** (card C1 owns): `data/<company>/consume/<project_id>/dashboards/<id>.json`: `{id, title, project_id, tiles:[{id, title, kpi, sql, spec, note, state: proposed|accepted}], audience:[user ids or groups], refresh: same|daily|weekly, created_by, updated_at}`. Tile SQL is SELECT-only over the project's gold (and silver read-only) tables, validated by the program and run by the program; `spec` is a **Vega-Lite** JSON spec without data; the program injects rows. Lumen never writes figures into text.
9. **Charting**: Vega-Lite through `vega-embed` (npm: `vega`, `vega-lite`, `vega-embed`; card C2 adds them to `ui/package.json`, the only card allowed to). Reason: a declarative JSON spec an agent can write and the program can validate; no code execution; covers bar, line, area, table, KPI number.
10. **Pictures of a wanted visual** (Consume): read locally first (OCR for titles, axis labels, legend words) and described to Lumen as words. Sending the image itself to a model is allowed only when the uploader ticks "This picture contains no client figures" (recorded); otherwise only the local reading is used.
11. **The three agents' skills**: `skills/north/`, `skills/span/`, `skills/lumen/` (card G1 owns all three folders and the router keys). Model router keys: `north`, `span`, `lumen`.
12. **Shared files** owned by one card only: shell and copy (S1), `ui/package.json` (C2), `skills/*` and router config (G1), `e0a_catalogue.py` (D1). Everyone else lists needed changes under "Wiring for the orchestrator".
13. **Tests**: own file only, tmp plane, `SH_MODEL_PROVIDER=off`; UI cards run tsc and their vitest. Do not run the whole suite. No server restart, no vite build, no live data writes, no secrets printed, no Claude attribution. Back up any existing file before editing (`.sh-tmp/<name>.bak-<id>`).
14. **Copy**: plain business English for non-technical people; every button states what it does; status words always written.
