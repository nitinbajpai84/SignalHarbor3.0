# L2 Proposed changes (accept or not)

## Reuse check
- Storage and atomic writes: `sh_platform/jsonfile.py` (`lock_for`, `write_json_atomic`, `read_json_strict`), as P1 comments do. Nothing new.
- The trail: P1's `comment(..., kind="change")` and its `_change` (set resolved). No new comment code.
- Access: the v1 `g1_access.intent_gate` already covers every route with `{iid}` (GET needs "read", POST needs "full"). No ad-hoc role check on project reads; only the per-document writer roles are checked again in the handler.
- Each engine keeps its own merge/apply logic and calls it from `apply_proposal`. The ChangeBar from L1 is extended, not replaced.

## What changed
- `sh_platform/v1/l2_proposals.py`: `propose`, `accept`, `reject`, `pending`, `facts`, `view`, `resolve_words`, `diff`. A proposal is `{id, document, summary, changes[{op,path,before,after}], by, at, status, payload}`. Stored in `projects/<pid>/proposals.json`, or `intents/<iid>/proposals.json` before the project exists (and kept there if the project comes later). `accept` claims the proposal under the file lock (pending to applying), applies it through the engine with no lock held, then marks it accepted: two accepts at once apply it once, the second gets 409. A failed apply puts it back to pending. A newer proposal for the same document replaces the pending one.
- Engines (each exports `apply_proposal(plane, iid, proposal, who)` and a `propose_*` helper):
  - `i6_chat`: the model's SOW patch (document `sow`) and process steps/handovers (document `process_map`) are proposals; the SOW is not written. The "North wrote" snapshot is taken only when North writes (the rules-only path, or an accept), and an accept keeps the old value in the snapshot for any cell the person had changed, so the person's edit stays theirs after the accept too.
  - `a1_chat`: data model, questions, scope (document `design`). Design/scan/mapping steps still run at once (they are actions, not patches); the blueprint default data model is not filled in while a model proposal is pending.
  - `f1_chat`: the model's "change" or "sql" reading of the engineer's answer (document `mapping`). Pasted SQL and the rules-only reading apply at once. A "yes" or a bare "no" that settles a proposal is not read as the answer to the next point.
  - `c3_chat`: the model's brief patch (document `brief`); changes are shown by KPI and feed name, not code. A dropped dashboard file is still kept at once.
- The rules-only fallback (model off) applies as before: it parses the person's own words, so it is the person's own input.
- Words in chat: a message that is essentially a yes ("yes", "accept", "ok", "looks good", up to eight words, nothing else in it) accepts the pending proposals of that agent's documents; a bare "no" of up to four words, or a message starting "not this", "reject", "that's wrong", "don't change", turns them down and the whole message is the reason. The reason, and what still waits, reach the agent next turn as `turned_down_by_the_person` and `proposed_waiting_for_the_person` (digit-free handles).
- When North/Span/Flow/Lumen proposes, the turn is not "ready" and the reply ends "I have proposed N things to change; say yes to accept, or tell me what is wrong." so nothing is closed over an unaccepted change.
- Accept records a resolved comment of kind `change` on the document line: "North changed the Net worth definition and 2 more; accepted by Meredith" (line found by matching the first changed row's name against the numbered lines; none if no project).
- Routes (`l2_routes.py`, `l2.permissions.yaml`): `GET /api/v1/intents/{iid}/proposals`, `POST .../{pid}/accept`, `POST .../{pid}/reject` `{reason?}`. The chat views (`north`, `span`, `flow`, `lumen`) also carry `proposals: {pending, recent}`.
- Downstream: proposals live in their own file and never in the SOW, design, mapping or brief records, so P1 documents, sign checks, exports and every agent that reads the records see only accepted content.
- UI: `workbench/ChangeBar.tsx` (summary, Accept, Not this with an optional "Why not?"), `workbench/proposals.ts` (`useProposals`), `ChangedLines` inside each document that lists its changes (green new, amber changed with the old text struck, red struck-through removed), and the text of an existing line that a proposal changes or removes is marked in the document until decided. Wired on the four screens.

## How to test on the demo
1. Sign in as Arjun Mehta, open `/centre/intent`, say "Net worth by entity every month". With the model on, North's reply ends with "I have proposed N things to change"; the Intent of work document is still empty, and the bar above the documents shows North's summary with Accept and Not this; green lines list the new rows.
2. Type "yes" in the chat (or press Accept): the SOW fills in; open the project's Intent of work and see the resolved "North changed ...; accepted by Arjun Mehta" note on the line.
3. Edit a definition by hand, ask North to reword it: the proposal leaves your edit out. Press Not this, type a reason: nothing changes, and North's next turn knows why.
4. Repeat on Span (data model and questions), Flow (answer a mapping point: the row changes only after Accept) and Lumen (brief).
5. Sign in as someone not on the project: the list and the accept both answer "not open to you".

## Known limits
- The change highlight inside a document is by text match for changed and removed lines, and by the list at the top of the document for new lines (a new line is not in the document yet). It is not checked in a real browser (no servers started).
- A proposal cannot be partly accepted; "Not this" drops the whole proposal. Accepting needs the project's team plus the document's writer role (design, mapping: analyst or company admin; brief: analyst, sponsor or company admin; intent of work: any team member).
- A pending proposal does not stop signing (it is simply not content). Add a sign warning if wanted.
- The rules-only fallback and pasted SQL are applied at once by design (the person's own words).
- Proposals from the model-off path are never produced, so the demo with the model off shows no proposals.

## Fixes after review
Review: `REVIEW-L2.md`. Backups: `.sh-tmp/*.bak-l2fix`.
- Pending proposals now stack. The "replaced" loop in `propose` is gone; one "yes" accepts all of a document's pending proposals in order. The ChangeBar and `tail()` already counted a list.
- "No ..." only rejects when it is a bare no (up to four words, e.g. "No, liabilities count too") or starts with "not this", "reject", "that's wrong", "don't change", "turn it down". "No, we have never measured it" goes to the agent as an answer. A yes is accepted only when the message is essentially an acceptance (up to eight words, only filler such as "please", "thanks" after it), so "Approved by the board last year" does nothing.
- Flow: on accept, a cell (source field, transformation, rule) whose current value differs from the proposal's `before` is left as the engineer has it; the accepted proposal carries a `note` saying so. If every cell changed, the accept is refused with a plain message and stays pending.
- Signed documents: `L2.accept` checks the project artefact (`intent`, `design`, `build_pack`, `brief`) first; if signed, the proposal becomes `superseded` with the reason "The document was signed, so this change can no longer be made." and the accept answers 409. Pending proposals of a signed document are marked `superseded` whenever the proposals are listed or the chat reads them. They show among the recent ones.
- "applying": the claim stamps `applying_at`; one older than a minute (or with no stamp) is read as pending again, so a crash no longer strands it. Apply is by name match, so a second try does not duplicate. The revert comment now says an engine may have written part of it.
- Model-off fallback (known limit, not a defect of this card): it applies at once only the person's parsed words. Two things on that path are not the person's words and still land unasked: KPIs suggested from the industry pack (`i6_chat`, `N.pack_suggestions`) and Span's blueprint default data model (filled whenever no proposal is pending, model on or off). Both were so before L2. With the model off, no proposals are made, so the demo shows no ChangeBar.
