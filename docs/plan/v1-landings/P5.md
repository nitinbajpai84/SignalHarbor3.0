# P5 Ops hand-over and tickets

## Summary
1. `POST /api/v1/ops/handover/{pid}` (the builder hands over) and `POST …/accept` (ops accepts, so the project's stage becomes `live`). The builder and ops are written to `people` if nobody holds those parts yet.
2. The offer is also a build-pack comment of kind `handover` addressed to the project's `ops` part. P1 sends it to the raiser while nobody holds `ops`. It is resolved on accept, so Pulse drops the card.
3. Tickets: ops raises one with `POST /api/v1/ops/tickets` {pid, source_id, text}, or the Watcher raises one automatically. It is a build-pack comment of kind `ticket` addressed to the builder, written through P1 (guarded). `build/ops/tickets.json` is the ops ledger and, while P1 is absent, the only place a ticket lives.
4. The Watcher hooks into b5's ops read. On a live project, a source that is late, has not arrived or failed its checks raises one ticket per source per day. The same read writes each live project's daily state to `build/ops/daily.json`, which Pulse can read through `p5_handover.daily(plane, pid)`.
5. A HandoverCard sits on the ops page (accept, daily state, raise a ticket) and on the engineer page (hand over). Sources that are on time now keep their Loaded buttons folded under "Daily state: on time. Give a word for <period>". Sources that are late or failed, or marked Not loaded, still show the buttons in the row.

## Open questions
- `build/ops/handovers.json`, `tickets.json` and `daily.json` are P5 ledgers that are not in the records contract. Pulse may want `daily(plane, pid)` in its "your projects today" line; it does not read it yet.
- The Watcher raises tickets only on **live** projects (after hand-over). Before then, failed checks are Flow's open points on the engineer page.
- With P1 present, the card reads each ticket's comment state from P1, so a ticket resolved on the build pack leaves the card. Ledger-only tickets (P1 absent) have no resolve route; add one if P1 is ever absent in practice.
