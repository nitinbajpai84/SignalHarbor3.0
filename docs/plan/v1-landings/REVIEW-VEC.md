# Review: V1 Search by meaning (hybrid RAG)

Reviewed 8 Oct. Code: `sh_platform/v1/doc_index.py` (diff vs `.sh-tmp/doc_index.py.bak-vec`), `sh_platform/v1/doc_embed.py`, `tools/reindex_vectors.py`, `tests/v1/test_vectors.py`, root `conftest.py`. Landing: `docs/plan/v1-landings/VEC.md`.

## Verdict: **not yet** — two blockers, both small fixes. The access boundary, the stale-vector handling and the fusion are right.

Tests: `SH_MODEL_PROVIDER=off python -m pytest tests/v1/test_vectors.py tests/v1/test_doc_read.py -q` → 16 passed in 7 s. Full `tests/v1` (minus test_proposal_speed): see the line at the end.

## What holds
- **Access**: `_vector_hits` (doc_index.py:258-279) selects `vec_files` joined to `files` with `f.path in (paths)` and then `vectors where path in (have)`; the text backfill at :316 queries by the (path, l1, l2) that came from those two lists. No row of a path that `doc_tools` did not pass can come back; `doc_tools._files` still filters on ticked + readable + `is_file()`. `test_vectors_never_returned_for_paths_not_passed_in` covers it.
- **Stale vectors**: `ensure` deletes `vectors` and `vec_files` inside the same transaction that rewrites `lines` and `passages` (:121-128); `_embed_file` re-checks `files.sig` under the file lock before writing (:222) and `_vector_hits` only trusts vectors whose `vec_files.sig` equals `files.sig` (:263). I could not build a path where vectors of version A are mixed with passages of version B, or l1/l2 that do not exist in `lines`.
- **Fusion**: ties between a words-only and a meaning-only hit fall to words (words inserted into `score` first, `sorted` is stable). A passage in both lists always beats one in a single list. The 0.45 floor is applied before ranking, so a weak meaning hit never enters the list at all.
- **Fallback**: `Unavailable` is caught in both the background job and the query path; the warning fires once; `test_fallback_when_the_model_fails` proves words-only output is identical.
- **Network**: fastembed 0.9.0 tries the HF cache with `local_files_only=True` first (model_management.py:665-680) and only goes to the network when the cache is incomplete; no telemetry call exists in that path (huggingface_hub only adds a user-agent header to download requests). `data/_models/models--Qdrant--bge-small-en-v1.5-onnx-Q` is already present on this box, so no download happens in the demo.

## Blockers

### B1. A failed model load is never remembered: every background job and every search pays the full download attempt again (doc_embed.py:27-37, doc_index.py:204-235, :267-268)
`_load` leaves `_model = None` on failure, so every call to `embed` retries `TextEmbedding(...)`. When the model is not in the cache and the box has no route to huggingface.co (the exact deployment the card sells: "nothing leaves the machine"), fastembed makes 3 attempts with HF connect timeouts of 10 s and sleeps of 3 s and 9 s between them (model_management.py:688-750): about 40-60 s per `_load`, under `doc_embed._lock`.
Scenario: a company with the model never downloaded. Every search queues up to 4 backfill jobs (:267); each job spends ~45 s failing inside the **same 2-worker pool that does OCR** (`_bg`, :137), so a PDF uploaded during that time shows "still reading" for minutes; the pool is then clogged again by the next search. Only one warning is logged. North keeps answering (words only), but uploads and scans stall, and CPU/network retries never stop.
Fix (one line): remember the failure in `doc_embed` (a module flag set in the `except`, re-raised as `Unavailable` on later calls; cleared only on process restart or `reindex_vectors`). Optionally retry once an hour.

### B2. Background embedding jobs escape the test fixture and can load (or download) the real model during the suite (conftest.py:14-22, doc_index.py:200-201)
The autouse fixture patches `doc_embed.embed` for the test's duration only. `ensure` submits `_embed_file` to the real `ThreadPoolExecutor` (only `test_vectors.py` patches `_submit` to run inline). A job that starts after the test's monkeypatch is undone — the pool's two workers are busy with a picture OCR in `test_pictures.py`, or the box is slow — calls the real `doc_embed.embed` → real `fastembed` load (and, on a clean CI box, the 70 MB download into `data/_models/`). The landing's claim "tests never load the real model" is therefore not guaranteed. It passed here because the model is already cached and the pool is usually idle.
Fix: in the same conftest fixture also `monkeypatch.setattr(doc_index, "_submit", lambda fn, *a: fn(*a))` (the stub raises `Unavailable` synchronously and `_warn` handles it), or set `doc_embed._model` to a stub object for the session. Either is two lines.

## Should-fix
1. **Query embedding waits behind a whole-file embedding** (doc_embed.py:44-46). `embed` holds `_lock` for the entire encode. A 1,000-passage file in the background (10-20 s of CPU for bge-small) makes North's search wait that long on the query embed. Use `_lock` for the load only; `onnxruntime.InferenceSession.run` is thread-safe, and fastembed's `embed` does not share mutable state across calls. If you want one encode at a time, at least split a file into batches of ~64 so the query can slip between them.
2. **A dimension or blob mismatch kills every search, not just the meaning half** (doc_index.py:276-278). Switch `SH_EMBED_MODEL` to a 768-d model without `--all` reindex, or one corrupted blob, and `reshape`/`m @ q` raises `ValueError`; it is not `Unavailable`, so it escapes `_vector_hits`, the tool loop returns "The tool could not run" (loop.py:153-157) and North has no document search at all. Catch `Exception` in `_vector_hits` as "words only" (one log line), and store the model name in `vec_files` (or `sig = f"{MODEL}:{sig}"`) so a model switch reindexes itself instead of relying on the operator reading the landing.
3. **A changed file's new vectors can be dropped until the next search** (doc_index.py:245-255). `_embed_later` returns when the `vec:` key is busy. If version A is still embedding when `ensure` writes version B, A's job sees the sig change and returns without writing, and B's job was never queued. The next search backfills it, so it heals, but the doc says "re-embedded with the file when it changes". Fix: have `_embed_file` re-check `files.sig != vec_files.sig` at its end and requeue itself once, or keep a "dirty" set.
4. **Non-ASCII queries never reach meaning search** (doc_index.py:282-292). `_match` keeps `[A-Za-z0-9]+` only; a Chinese query gives an empty `q` and `search` returns `[]` at :291 before `_vector_hits` runs. The landing's "meaning search carries Chinese until [a tokenizer] is added" is false today. Either run the vector half when `q` is empty, or drop the sentence from the landing.
5. **`reindex_vectors.py --all` bypasses the in-process busy set and the server's file lock** (tools/reindex_vectors.py). `lock_for` is a threading lock, so a running server and the script only have SQLite's own locking (30 s busy timeout). The two writes are each one short delete+insert transaction, so I found no duplicate-row path, and a concurrent server job merely rewrites the same vectors. Acceptable, but say in the docstring "stop the server or expect one 'database is locked' retry under load"; also set `logging.basicConfig(level=WARNING)` so the "model not available" warning is visible when the script prints `files with vectors: 0`.
6. **Deleted files keep their rows** (pre-existing, now bigger): `c4_library.delete` unlinks the file (c4_library.py:254) but `files/lines/passages/vectors` stay. `doc_tools` filters on `is_file()`, so nothing leaks, but the index of a company only grows; `reindex_vectors` re-embeds deleted files. A `doc_index.forget(plane, path)` called from `delete` is five lines.
7. **Offline after the first download**: set `HF_HUB_OFFLINE=1` in `_load` once `CACHE / "models--Qdrant--..."` exists (or always, falling back to a one-time download when the cache is empty). Today a corrupted-cache exception (model_management.py:681) silently goes to the network.

## Nits
- RRF with `limit*3` candidates per list means the final 5 interleave as words #1, meaning #1, words #2, meaning #2, words #3: a query with five exact keyword passages shows three of them plus two meaning hits ≥0.45. Expected RRF behaviour, not a bug, but note it in the landing so nobody files it as "search lost a result". `_match` is an `OR` over up to 12 words, so the "words" list is itself permissive (a figure like `2024` matches many passages).
- `_vector_hits` loads every vector of the ticked paths per search (1.5 KB each). Fine for a conversation's handful of files; the `ponytail:` comment already names the ceiling.
- `_warned` and `_failed` (if added) are plain module globals written from two threads; harmless.
- `search` opens three connections per call (`_ready` → `ensure` opens two more per path) and runs `executescript(_SCHEMA)` on each; pre-existing pattern, now with two more `create` statements. One connection per `search` would halve the SQLite chatter.
- `test_synonym_found_by_meaning_only` calls `DI.search` three times for one assertion; one call into a variable.

## `how` on North's source chips
Not now. `doc_tools.given` already has a `how` with a different meaning (`search`/`read`, used by `chips()` to pick what was read on purpose), and `SourceChips.tsx` renders file + lines only. A "found by meaning" marker would be useful for trust ("why did North cite this?") but it is a product decision for the Pulse/Consume chips, not this card: if wanted, add `found: words|meaning|both` to `given` in `doc_tools.search` (one key) and let the chip show a small "≈" for meaning-only hits. Keep `how` on the `doc_index` hit as is.
