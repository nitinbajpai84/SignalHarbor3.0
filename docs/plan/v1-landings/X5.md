## What landed
- `sh_platform/v1/skill_loader.py` (landed first): `load_skill(name)` joins `skills/<name>/` playbook, questions, traps, examples (then any other `.md`), trimmed to 6,000 characters; "" for a missing folder or a name with a path in it. `skill_label(name)`: the playbook's first heading.
- `skills/north/`: playbook.md (family office month-end, the usual KPIs and how each is worked out, usual sources, what documents carry), questions.md, traps.md (contradicting documents, ownerless decisions, one field under many labels, stale valuations, layout changes, scan-like text), examples.md. Drafted from FAMILY-OFFICE-PRD.md and the FO-DEMO answer keys; no party names. 4,304 characters.
- `sh_platform/v1/x5_extract.py`: the spec (`intents/<iid>/extraction.json`), the reading (`extractions/<doc_id>.json`), checks (present, parses, range `lo..hi`, ties_to `sum of: a, b` or `landing/<csv path with {field}>#<column>`, optional ` within N%`), the review queue, accept with correction (each correction becomes a worked example), and the revised spec after a layout change (two documents of a type failing the same way: the new label comes from the model's line pointer or from the person's correction; before and after on two documents; yes bumps the version, keeps the old in `previous`, and re-reads the documents still in review). The model sees only lines carrying a field's words, names masked, wrapped as untrusted text, each line under a letter alias; it answers line alias plus label, and the program copies the value from that line. With the model off, the same labels are looked up by rules. A failed check never guesses.
- `sh_platform/v1/x5_routes.py`, `x5.permissions.yaml`: 8 routes (see the file's docstring). Spec and revision: decision maker; run, detail, accept: analyst or company admin; queue and overview: company_admin, sponsor, analyst.
- `sh_platform/v1/i6_chat.py` (small, additive): goal `extraction` after `documents`; `EXTRACTION_PROMPT` and North's skill appended to the static prompt; `extraction_specs` in North's context; the model's `extraction` key goes to `x5_extract.from_chat` (confirmed types are read at once); dropped documents a confirmed type covers are read (`run_new_files`); the closing summary adds "What I will take out of the documents" and the queue line. All through a guarded `_x5()`: a failing extraction never breaks the talk. System prompt with the skill: about 11,500 characters.
- `ui/src/v1/x5/`: `ReviewPage` at `/centre/extract/review` (the queue, the passage with the value's line marked, a box per value, Accept) and `ExtractionPage` at `/centre/intent/:iid/extraction` wrapping an exported `SpecPanel` (types, fields, checks, worked examples, Confirm this list, revised spec with before/after and yes/no, documents read, "Propose from this document").
- `docs/product/SOW-DONE-CHECKLIST.md`: item 15 (extraction), a line in the closing move, and (15) in what the architect takes.
- Tests: `tests/v1/test_x5.py` (3 tests: loader; stub model confirms a spec in the chat, layout-B document goes to review, a second one drafts the revised spec, yes clears the queue and keeps version 1 for the older document, every message to the model passes the gateway checks and carries no name; model off: rules propose, the analyst may not confirm, a bad correction is refused, a correction becomes a worked example and drives the revision). `ui/src/v1/x5/x5.test.tsx` (2 tests: accept posts the corrected value; refusal).

## How to test by hand (8400, after the orchestrator serves)
1. Sign in as Arjun Mehta (Neera, decision maker). Intent Centre: start a talk ("Monthly statements into a valuation table") and add two or three statement-like documents with the paper-clip (any from `data/ardmore-1/documents/01..03` work, or D5's two-layout files once landed).
2. With the model on, North proposes what to take out of them and asks you to confirm; say yes. With the model off, open `/centre/intent/<iid>/extraction`, type a file name (for example `01-statement-summary-2026-06.md`) in "Propose from this document", then "Confirm this list" (1 click).
3. The panel lists "Documents read" with Read or Needs a look, and the strip says "N documents need a look".
4. Sign in as Leela Raman (analyst). Open `/centre/extract/review`: the passage shows with the value's line marked; type the right value into the box and press Accept (2 clicks). A wrong value ("SGD x" for a number) is refused with a sentence.
5. Add a second document in the changed layout (D5's format B). Back as Arjun on the extraction page: "North suggests a revised spec" with before and after on two documents; press "Use the revised spec". The version goes to 2 and the queue empties.
6. As Leela, `PUT` on a spec (Confirm this list) is refused: only the decision maker confirms.

## Open questions
- Fields added to the contract: per type `state` (proposed / confirmed), `previous` (older versions kept for older documents), `revision` (the pending draft); per extraction record `doc_id`, `file`, `intent_id`, `type_name`, `failed_first`, `at`, `accepted_by`, `accepted_at`, and per value `{value, raw, line, by}`.
- `extractions/` sits at the company plane (one queue across intents); the card did not say whether it belongs under the intent.
- ties_to has no default tolerance (exact to one unit unless the spec says "within N%"); the tolerance belongs to the reconciliation policy, not to code.
- Accept takes the document out of the queue even if a check still fails after the correction (the person has looked); confirm that is the wanted rule.
- Who may run the reading and work the queue: set to the data engineer seat (analyst, company admin); the card does not name the seat.
- A document a confirmed type does not obviously cover (file name shares no word with the type or its samples) is not read automatically; North or the person names its type.
