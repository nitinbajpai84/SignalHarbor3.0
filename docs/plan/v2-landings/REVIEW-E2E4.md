### B4 · Recommendation 2 not implemented: nothing happens until Operations confirms
Today `e2_extract.extract` (`e2_extract.py:94-127`) only writes `extracted_fields` with the nav `pending`. The valuation row, `e3_impact.on_new_valuation`, the case and the Pulse cards all wait for `confirm` (`:167-212`). So after the amended statement is read the CIO sees nothing, no case exists, and Operations' only prompt is E5a's "Check the figures" document card. Exactly what must change:
1. `sh_platform/v1/e2_extract.py`: pull `confirm`'s lines 189-209 into `_record_valuation(plane, field, amount, approval_status) -> valuation id` (instrument, confirmed date/currency, `prev` lookup, `e1_write.record` with `supersedes_id`). In `extract`, after the fields are inserted (after `:126`), when a nav was found and the document has an instrument, date and currency: `vid = _record_valuation(plane, nav, nav["value_numeric"], "pending")` then `exc = e3_impact.on_new_valuation(plane, vid)`. The pending row supersedes VAL-1 so E3c computes the 180,000 USD effect and opens the case with `exception_impacts` at extraction time; E5a's `_exception_cards` then gives Operations and the CIO their cards from the open revision case with no change. Return `exception_id` from `POST .../extract` (`e2b_routes.py:31`).
2. `confirm`: `_record_valuation(..., "confirmed")` (the new row supersedes the pending one; append-only, both stay). Then find the open revision case for the instrument (`select id from exceptions where instrument_id=? and exception_type='revision' and status in open states`) and `e4_cases.add_event(plane, exc, viewer, "valuation_confirmed", "Operations confirmed the manager-reported valuation of {amount} {ccy} read from the amended statement.", evidence_document_id=doc)`; return that id. Only when no open case exists fall back to `e3_impact.on_new_valuation` (first-ever statement). A `corrected` value that differs from the pending one should also append a note with the corrected figure (the impacts keep the draft value read from the page; say so in the note).
3. `sh_platform/v1/e1_reports.py:184-185`: a superseding row counts as `revised` only when `cur["approval_status"] in ("confirmed", "approved", "approved_official")`, else the line's status is `unverified`. That is what makes the CIO Brief show the indicative change labelled unverified (E5b already banners `unverified` lines and names the open case) and keeps rec 1 (an unverified value never enters a certified metric; E3d already maps a non-approved row to `unverified`).
4. `sh_platform/v1/e3_impact.py:84`: title and description per rec 3 (see S1), and `portfolio_id` fallback (see B6).
5. `tests/v1/test_e2b.py`: one test: extract the amended statement → a `pending` valuation superseding the first, the stubbed impact called once, `exception_id` returned; confirm → a `confirmed` row superseding the pending one and the `valuation_confirmed` event (stub `e4_cases.add_event`).

### B5 · E4a: actions run before the access check; the owner can dismiss a material case
- `e4a_routes.py:45-46` `_act` runs the action, then `C.get` (which is where `_can_see` lives). `take`, `submit`, `dismiss`, `assign`, `ask_finance`, `note` (`e4_cases.py:206-337`) never call `_can_see`. Scenario: Rina (participant, no E1d scope; `test_e4a.py` shows `listing` hides everything from her) posts `/api/v1/cases/CASE-0001/take` → she becomes owner and from then on sees the case. Fix: `_act` → `lambda p, v: (C.get(p, cid, v), fn(p, v), C.get(p, cid, v))[2]` (one line), or `_can_see` at the top of each mutating function.
- `dismiss` (`e4_cases.py:314-325`) closes any open case, including `waiting_check` and `material`, for whoever is `mine` (`_may:357`): the maker submits, then dismisses her own material case; no second person. `test_e4a.py:87` even exercises this (Mei dismisses the material case she owns). This contradicts the module's own rule ("a material or unrated case closes only through a check"). Fix: in `dismiss` and `_may["dismiss"]`, when `materiality_status != "below_threshold"` require `me not in (owner, maker)` (another person dismisses, with reason) and refuse in `waiting_check` for the maker.

### B6 · The Fund A case is invisible to Operations: the valuation row has no portfolio
