# B2 landing: Span, the build agent

Files: `sh_platform/v1/b6_plan.py` (plan store, SQL checks, approval, state hooks), `b6_span.py` (rules plan, model for unplaced KPIs, conversation), `b6_routes.py`, `b6.permissions.yaml`, `tests/v1/test_b6.py` (8 pass).
Test: `SH_MODEL_PROVIDER=off python -m pytest tests/v1/test_b6.py -q`

How it works
- `propose_plan` reads the signed intent (sources, KPIs), approved `e0b_mappings` and the catalogue. Bronze per source layout (`bronze_<code>_<layout>`, no SQL, landed by intake); silver = `insert ... select` into the core table with `try_cast`, plus `uuid()` for `id` and the company org id; gold = `create table gold_<slug>_... as select` per KPI group (measure by name/synonym, period from the KPI, one dimension on the fact table or one join away). A KPI the rules cannot place is named in `notes`, never guessed; with a model on, only those KPIs go to the model (column names only) and its SQL passes the same checks.
- Every statement is parsed with sqlglot (DuckDB): one `create table as select` or `insert ... select`; DROP/DELETE/UPDATE/ALTER refused; each table read must be in the catalogue or earlier in the plan and listed in `depends_on`; every column resolved. Gold columns and `lineage` are derived by the program.
- Approval: architect seat, never the proposer; approves the linked E0a model change in the same step; calls `E.register_bronze` / `E.register_gold` (only on approval); sets project stage `designed`; every step logged in `build/<pid>/log.jsonl`.
- Conversation: "add a monthly gold table by entity" becomes a pending change; "yes" / "not this" in the chat, or the accept/reject routes, resolve it. Accepting saves the next plan version, which goes back to the head of data.

Routes (as `ui/src/v1/b6/api.ts` expects): `GET /api/v1/build/projects`; `GET .../plan` (plan plus `model_diff`, `is_new`, `can`, `versions`, `changes`, `log`; `plan: null` when none yet); `POST .../plan/propose`, `/plan/approve`, `/plan/reject`; `GET|POST .../chat` -> `{turns, pending}`; `POST .../plan/changes/{cid}/accept|reject`.
Differences from B1's assumptions: `model_changes` is the E0a proposal number (integer), not a string; `can` also has `propose`; `projects` rows also carry `intent_signed`; `plan` GET adds `title`, `intent_signed`.

For B4 (runner): `b6_plan.get(plane, pid)`, `set_state(plane, pid, "built"|"live", by)`, `set_schedule(plane, pid, {...}, by)` (approved plans only, logged). Bronze tables have empty `sql`: skip them, intake fills them. `can.run_sandbox/go_live/schedule` are decided here from state and seat; B4 may refine.

Wiring for the orchestrator
- Nothing else needed; routes and permissions auto-install by the card pattern.
- Optional: on `propose`, add a card in Action for the head of data (no Pulse extension point touched here).
- L2: its `DOCS` is closed to intent documents, so build-plan changes use their own pending list; register a `build_plan` document there if one Accept/Not this inbox is wanted.

Known limits: sheet `transform` text is not applied (text is cast to the column type); required columns beyond `id` and `organization_id` are not supplied, so a sandbox load of silver may need B4/E0c to fill them; "by entity" resolves only when a mapped foreign key leads to a table with a matching column (the join gives an id, not a name); gold has no approval-status filter.
