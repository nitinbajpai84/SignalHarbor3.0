# B4 landing: pipeline runner and scheduler

Files: `sh_platform/v1/b6_run.py`, `sh_platform/v1/b6_schedule.py`, `tests/v1/test_b6_run.py` (10 tests pass).

API (for B2's routes): `b6_run.run(plane, pid, mode, plan=None, by=None) -> run record`, `latest_plan`, `runs(plane, pid)`, `Refused(message, status)`;
`b6_schedule.airflow_dag(plane, pid)` (text for download), `export_airflow(plane, pid)` (writes `data/<company>/airflow/<slug>.py`), `tick`, `on_arrival`, `start`, `stop`.

Behaviour: dependency order; per step build `<t>__next` and swap in one transaction (failure rolls back, previous table intact, run stops, later steps "not run");
tables with empty SQL are bronze ("filled by file loads"). Sandbox = fresh copy `warehouse/sandbox.duckdb`; live needs plan state approved/built/live.
Sandbox ok moves approved to built; live ok moves to live (only the `state` key of the plan file is written). Live runs write Action cards (`pulse_items`):
failed to the plan's `proposed_by`, refreshed to each dashboard `audience` entry (matched on user id, external identity, display name or email).

Wiring for the orchestrator:
1. App start: `b6_schedule.start(lambda: [store.get(c) for c in store.list_company_ids()])` (check the PlaneStore accessor name); stop on shutdown with `b6_schedule.stop()`.
2. Intake (E0c load, after status `loaded`): `b6_schedule.on_arrival(plane, source_code)`.
3. B2 routes: `/run?mode=` -> `b6_run.run`, `/runs` -> `b6_run.runs`, `/airflow` -> `b6_schedule.airflow_dag`; schedule edits are B2's plan-file write.
4. D1: register gold tables in the catalogue after a first live ok (not done here).
5. C3 also writes "refreshed" cards for dashboards; a person may get both (this card's is about the data, C3's about the tiles). Drop one if too noisy.
Limits: Airflow DAG is generated text, never executed or imported here; no E1d access check on the refreshed cards (audience was checked when it was set).
