# Module 2: Baseline

Takes the signed charter and produces the process map and the data catalogue. Agent: Lens, the business analyst; Nira coordinates.

- Spec: `docs/specs/MODULES-1-2-FEATURE-SPEC.md`, features M2-xx and X-xx. Screens: `docs/specs/Module 2 Baseline process and data mapping.pptx`. Catalogue template: `docs/specs/signal-harbor-data-catalogue-template.xlsx`.
- Starts from the signed charter, or from a list of measures the customer uploads when module 1 was not bought.
- Per KPI: triage, nominate business, data and process owners, governance, requests to owners (email link or account), sensing, upstream and downstream trace, process map, catalogue, review and sign.
- Lens drafts from the company's own industry pack and labels every draft. It never invents a formula; a missing formula is a question.
- Lens is the main agent of the module and has its own docked block on every screen (api/lens_chat.py, ui agents/); Nira is one small strip inside it, her facts built from the baseline's state (agent/nira.py over sh_platform/agents/guide.py). Before the work list, "Give Lens what you already have" tags the company's own context documents by kind (store/lens.py `inputs`); on opening, Lens fills what it can (marked guessed, with the document title) and people only review the gaps. A suggestion's draft waits in lens.json until a person confirms the measure; no measure exists before that.
- Lens may read metadata (table and column names, types) read-only. Sample data and dictionaries are profiled locally; only names and types reach the model, never values.
- Each owner signs their own part; sponsors countersign. Signed content is read-only.
- Output: the process map and the Excel data catalogue (tabs: Sources, Tables, Fields, Extractions, KPIs). Module 3 reads only these.
- Technical definition and open questions (M2-E1): each measure carries `technical` {sources, tables, fields (ids of catalogue rows), calculation, filters, grain, period, currency_basis, notes} (each a provenance value; Lens's draft beside a person's part is `technical_proposal`; the data owner's confirmation `technical_confirmed` lapses when a part changes) and an `ambiguities` list. One helper (domain/ambiguities.py) builds and settles ambiguities for the glossary, governance and this package; governance ones are derived, never stored, and listed read-only. Lens drafts on open with ONE model call per measure for the parts and the contradictions (api/technical.py `draft_technical_items`, agent/lens.py `draft_technical`); code checks (domain/technical.py `code_ambiguities`) never need a model. Everything shown to a person is filtered per viewer (store/ambiguities.py `listing`, store/technical.py `hidden_terms`): the raw measure in the work list never carries these keys. `domain/readiness.py ready_to_build(kpi)` is what the sign-off gate (M2-E4) calls.
- Ready-to-build sign-off (M2-E4): both signatures are refused (domain/signoff.py `countersign`, `gate`) unless every measure is `ready_to_build` or was left out by the organiser or a sponsor with a reason (`leave_out`, kept on the sign-off version), the glossary is reviewed, governance is decided and no question is open; an accepted one travels as a known risk. The gate is worked out over every measure and row (domain/gate.py `check`, store/gate.py `compute`), so it is the same for everyone; `for_viewer` shows a person only the reasons about what they may see plus "Something restricted is still open". The signature covers two documents, "Business glossary" and "Data catalogue", each recorded on the version with a sha256 of its full content (store/documents.py; derived-column times are left out so a rebuild of the same content gives the same code). The hand-off gains `glossary`, `technical`, `ambiguities` (accepted only), `left_out` and `documents` (contracts/baseline_outcome.yaml `added_keys`; an older record lacks them), filtered by `handoff.for_viewer`. "Download the signed baseline" (store/bundle.py, GET `/signoff/bundle`) is one zip built for the viewer from the existing exports; before signing it is a draft marked "Draft, not signed".
- Business glossary (M2-E2): the one retrievable glossary document belongs to one baseline but sits in the company's shared documents, so another baseline of the same company can retrieve it; governance is decided per baseline. Wording of restricted measures is never a company document (it stays in glossary.json).
- Round-5 rules (critic): an answer is recorded on the question and changes nothing unless the person chose a part (`SA.answer` part + wording; `T.with_wording` keeps the old text in `technical_history`; never the bare answer). A data owner of any role reads and confirms exactly their own measures' technical definitions (`GET /my-technical`, confirm matched by account id; on the answer link `technical`, `technical_sign_in`, POST `/answer/technical/confirm`). A confirmation is per part (`T.to_confirm`, `T.confirmed_parts`). A question is stored only with real words (`A.usable`: not blank, not the template, not a request for catalogue ids), duplicates of one part are one item (`A.same`, `A.tidy`), and one whose cause is gone closes visibly (`T.sweep`, `cause` "has:<part>"). Lens proposes the catalogue rows the technical notes name (NEW_SOURCE, NEW_TABLE, NEW_FIELD lines, kept only where the passages say the name: `T.anchored`, `C.propose_rows`), guessed with the document title, and the measure links them by id. A field's business meaning is its own description, else "Not available yet". A re-added measure is no longer left out (`SignoffStore.forget_left_out`).
